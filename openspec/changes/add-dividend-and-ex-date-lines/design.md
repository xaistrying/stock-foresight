## Goals / Non-Goals

**Goals:**
- Dividend list, share issues, ex-date lines, the level note, the dividend-aware week and the week-1 fallback, each stating where its figure comes from and how old it is.
- Exactly one brief file knows the feed; the isolation test says so exactly.
- A completeness rule that is conservative where the evidence is thin, and says what it rests on.
- A pure, tested issue classifier and count-changing-issue helper that N3 and N2b reuse without change.
- Statements about adjusted history that depend on a runtime check of the stored bars, not on an assumed vendor lag.

**Non-Goals:**
- Totals, a net line, dividends times a share count, count or cost after an issue (N2b); announcement tags, insider sizing, shares outstanding (N3); tax, fees, yield; a trading calendar; fetching the feed; any route or UI.
- Learning the vendor's adjustment lag (only an upper bound, 3 sessions, is known). The brief instead checks, per ex-date, whether the stored bars look adjusted yet (Decision 16).

## Decisions

### 1. Where the code goes, and what it uses of N1

New modules in N1's package, one concern each, so none grows past a few hundred lines: `feed_source.py` (I/O, the only feed reference), `corporate_actions.py` (pure logic over `Event`s and dates), `adjustment_status.py` (pure), `week_move.py` (pure: week events, board move, week-1 recompute), `dividend_lines.py` (pure renderers of the market-derived lines) and `dividend_lines_holding.py` (pure renderers of the holding-derived lines). Section functions live in two new modules so the structural guards cover them: `sections_market_dividends.py` (takes `MarketFacts` only; matched by N1's `sections_market*.py` glob, so it may not contain the words `shares`, `cost`, `purchase`, `holding` or `level`, and reads only `MarketFacts` fields) and `sections_holding_dividends.py` (takes a `Holding` and `MarketFacts`). The fixed-sentence constants go in N1's `wording.py` (N1 D15 and its review fix: `fixed_sentences()` returns every UPPER_CASE string constant of that module, so the verb guard and the runtime scan cover a new constant without a list being edited), not in the new modules. The pure modules import `Event` only under `TYPE_CHECKING`, so they do not pull the feed package into their import closure.

Seams used in N1 (re-checked against N1's final code, see "Re-diff against N1 final 2026-10-12"):
- `MarketFacts` (built in `facts.py`) already carries defaulted `dates`, `opens`, `closes` and `model` (opens come from `prices.read_opens`, a read-only query). N2a adds two more defaulted fields: `feed` (the `FeedSnapshot` read through the adapter once per ticker; `None` means the feed was not read, and then no feed line is printed, which keeps every N1 test and golden file valid) and `ex_status` (pairs of an `Event` and its `AdjustmentStatus`, computed once in `gather_market_facts`). No new database read is added to `facts.py`.
- `TICKER_SECTIONS` in `compose.py` is an ordered tuple of `(TickerReport, redact) -> Lines`; N2a adds one entry, `_dividends` (the DIVIDENDS block: market-derived lines always, holding-derived lines only when `redact` is false), between `_next_five` and `_levels`. `_week`, `_next_five`, `_position` and `_levels` keep their place and call the new section modules for their extra lines. No section function is rewritten.
- `sections_market.week_lines` stays N1's function; for a one-event ADJUSTED week it replaces N1's move line and, in the unredacted copy, N1's inside/outside sentence with the combined line of Decision 10, and it appends the market-derived notes. N1's `WeekFacts.kind` (`first`, `no_match`, `no_band`, `band`) is the issued-entry lookup: N2a never reads the issued log and never calls its writer.
- `compose.TRIGGER_COUNTERS` is not touched (N2a adds no trigger).
- N1's final runtime scan (`compose._scan`) runs over every line the tool wrote, with the investor's level texts removed, after NFKC and format-character removal, for buy, sell, hold, confidence and market sentiment. Every N2a sentence is therefore a line that must pass it; the level notes never embed investor text.

Alternative considered: put the lines in N1 and the feed read in N1's script. Rejected: it puts the feed reference in a file that also reads the holdings, and the isolation test could then only allow a broader path.

### 2. One adapter, read-only, never able to start the snapshot

`feed_source.py` imports only `app.services.company_feed.store` (`latest_items`, `last_fetch`; both open the log `mode=ro` and read a missing file as never fetched). It does not import `fetch`, `snapshot`, `inputs`, `rss` or `summary`, so it cannot start a fetch and cannot import `vnstock` (the store and normalise modules are vnstock-free by the company-feed spec). Its one public read is `read_events(ticker) -> FeedSnapshot` (events, a feed status, the oldest stored event date, a count of rows it could not read). Its other public function is `snapshot_command(tickers) -> str`, because `snapshot_company_feed.py` contains the string `company_feed` and the isolation test greps every other file under `backend/app/` for it: the command text must live in the adapter, and renderers ask the adapter for it.

`test_company_feed_isolation.py` changes:
- `test_no_module_outside_the_package_references_the_company_feed`: exclude the adapter path from the offenders scan (the same way `OWN_FILES` excludes `db/company_feed_log.py`), nothing else.
- `test_only_the_script_and_the_tests_import_the_package_outside_it` (renamed for what it now says): the expected list becomes exactly `["app/services/brief/feed_source.py", "scripts/snapshot_company_feed.py"]`. An exact list, not a prefix, so a second brief file importing the feed fails.
- New: an AST check that the adapter's company-feed imports are `store` only; a subprocess check that importing the brief's run module leaves `app.services.company_feed.fetch` and `...snapshot` out of `sys.modules`, and one that importing the adapter alone leaves those two and `vnstock` out (N1's refresh path loads `vnstock` for the price loader, so `vnstock` cannot be asserted absent from the whole brief; the adapter is the file whose import closure matters here).
- Kept as they are: no route, no post-run hook, no startup or background task, the news agent and debate runner do not know the log, the log is gitignored.

Alternative considered: allow the whole `brief/` directory. Rejected: the owner's instruction, and it would let any section function open the log.

### 3. `Event` and parsing

```
Event(event_code: str, exright_date: date | None, record_date: date | None, payout_date: date | None,
      value_per_share: float | None /* VND */, exercise_ratio: float | None, published_at: date | None,
      issue_class: IssueClass | None /* only for event_code 'ISS' */)

IssueClass = BONUS | STOCK_DIVIDEND | RIGHTS_OFFER | PRIVATE_PLACEMENT | EMPLOYEE | OTHER   (an Enum; N3 reuses these names)
```
Built from `StoredItem.fields` and `StoredItem.published_at`. A date string is cut to its first ten characters and parsed with `date.fromisoformat`; a string that does not parse becomes `None` and increments `FeedSnapshot.unreadable`. A row without `event_code` is unreadable. The brief prints "<n> feed rows could not be read" when `unreadable > 0`, so a vendor format change is visible and not read as "none found". A read that raises (a locked or malformed log) is logged with `logging` and read as the status `unreadable`, which has its own sentence ("its stored events could not be read this run, which is not the same as none found or never fetched") and the snapshot command, so a feed problem never removes a holding's block and is never described as a missing fetch. One malformed row (not a dict, a number or date outside plausible bounds, a number too large to convert) is counted as unreadable and the other rows are kept. The title is not carried: N2a prints no stored text and the event holds no string from the row except the event code. The one thing derived from a title is `issue_class` (Decision 6), computed inside the adapter; only the enum value leaves it.

Duplicates: `latest_items` returns one row per `item_id`, but a re-published event with a changed title would be a new item. Cash dividends are de-duplicated on `(exright_date, value_per_share)` and issues on `(exright_date, exercise_ratio)`, so a repeat is never listed twice. This is a guard, tested with a synthetic repeat; two stored FPT employee rows share an ex-date with different ratios and stay distinct.

### 4. Dividend list

Cash dividend: `event_code == 'DIV'`, non-null `exright_date`, `value_per_share` finite and positive. Listed for a holding when `purchase_date < exright_date <= last_bar` (strict at the purchase date: a buyer on the ex-date does not receive that dividend, which is what an ex-date is). Ascending by ex-date, formatted `3,000 VND (ex 2025-06-30)`. "Source covers from <date>" is the oldest `published_at` over **all** stored events of the ticker, not over DIV rows (the 50-row cap applies to all codes: VPB's oldest event is 2022-07-19, its oldest DIV 2023-10-20). The list is not summed, not multiplied by shares, and has no total line; the DIVIDENDS block says nothing about a total. (Consequence: readers who wanted a total, 12 of 20 in Appendix G, still compute it themselves; N2b adds it.) With no `purchase_date` the list is replaced by "not listed, because no purchase date is entered".

Ex-dates after the last bar are not in the list; they go to Scheduled (Decision 8). A dividend whose ex-date is on or before the last bar but whose payout date is later is listed by ex-date only; the payout date appears only in the window line.

### 5. Completeness: `MAX_LAG_DAYS = 120`

A holding's list is **complete** iff `purchase_date >= oldest_stored_event_published_at + MAX_LAG_DAYS`. Reasoning: a dividend missing from the store was announced before the oldest stored event, so its ex-date is at most `MAX_LAG_DAYS` after that date; if the purchase is on or after that horizon, no missed dividend can have `ex-date > purchase_date`. When incomplete, the block adds "This list may be incomplete for ex-dates before <oldest + 120 days>" with the reason in one sentence and the stated lag. The horizon date is printed; the investor is not told the list is wrong.

`MAX_LAG_DAYS` is a named constant at module level with a comment: the largest observed announcement-to-ex lag is 85 days (SAB, 2022-12-07 to 2023-03-02); 120 adds about 40% margin over 85. Evidence (patch of 2026-10-12): 44 cash dividends in 9 tickers, maximum 85 days (SAB; the next is SAB at 81) and every other ticker 21 days or fewer, so the long lags look like a SAB trait. The value is still a margin over an observed maximum, not a proven bound (whether it holds beyond these 10 tickers is open). It is a date-arithmetic window, not a price-move threshold (Rule 3 is not engaged).

If the feed holds no events at all for the ticker (never fetched, or an `empty` fetch) the oldest date is unknown and the list is not shown as complete; the state sentence (Decision 7) says why. Alternative considered: treat a fetch that returned fewer than 50 events as full history. Rejected: the independent review found "under 50 rows means full history" unsupported, and the same conservative answer costs only a sentence.

### 6. Issue class in the adapter, and one pure count-changing rule

**Class from the title, inside the adapter.** The adapter derives `issue_class` for every `ISS` event from keywords in the stored title (NFC, casefolded; first match in this order): `STOCK_DIVIDEND` ("Trả Cổ tức bằng Cổ phiếu"), `BONUS` ("Cổ phiếu thưởng"), `RIGHTS_OFFER` ("Quyền mua"), `PRIVATE_PLACEMENT` ("riêng lẻ"), `EMPLOYEE` ("CBCNV"), else `OTHER` (also for a missing title). Only the enum reaches the brief; titles are still never shown, carried or logged. N3 reuses the enum and its names.

**Count-changing for the investor**: `issue_class in {BONUS, STOCK_DIVIDEND}` **and** `exright_date` not null **and** `exercise_ratio` finite and `> 0`. Ascending by ex-date, de-duplicated. `count_changing_issues(events)` returns them; `share_issues_between(events, after, upto) -> ShareIssues(issues, factor)` keeps those with `after < exright_date <= upto` and `factor = product of (1 + exercise_ratio)`. The ratio is "new shares per share held" (SAB 1.0 for 100%, VPB 0.2604104), shown as "26.04 new shares per 100 held".

Other classes and states:
- `BONUS` or `STOCK_DIVIDEND` with a null ex-date: "announced, no ex-date yet", on the Scheduled line, with its announcement date and ratio if stored; never applied, never in the factor. To keep stale rows out (VCB's 2019 and 2020 bonus and stock-dividend rows still have no ex-date) such a row is shown only when its announcement date is within `PENDING_ANNOUNCEMENT_DAYS = 365` of the last bar (VCB's 2026-04-28 bonus is 167 days before 2026-10-12). The 365 was accepted by the owner; the vendor replaces the row (same `item_id`, new version) when it sets the ex-date, so a dated one never shows twice. Rows past the 365 days are not dropped silently: the Scheduled area ends with one quiet line, `<n> older announcement(s) with no ex-date are no longer shown.`, where `n` counts BONUS and STOCK_DIVIDEND rows with a null ex-date older than 365 days before the last bar (owner decision 4). It is printed only when `n > 0` and the feed was fetched, and it is market-derived, so a redacted copy keeps it. On the stored data VCB would show its 2026-04-28 bonus and count the 2019 bonus and the 2020 stock dividend, so `n = 2`; the line is deliberately vague about which ones, because the brief cannot tell a lapsed announcement from a cancelled one.
- `RIGHTS_OFFER`: shown as "rights offer to shareholders: read the notice; not calculated", with its ex-date when set. Never applied, never in the factor. It appears under the share issues since purchase when its ex-date is in `(purchase_date, last_bar]`, on the Scheduled line when after, and as a window line when in the window.
- `PRIVATE_PLACEMENT`, `EMPLOYEE`, `OTHER`: not applied and not listed as share issues for the investor in N2a (N3 tags them). The rows they come from still count in "the source covers from" and in the unreadable count.

Why classes and not the code and ratio: the discussion's measurement shows ratio and ex-date do not separate the cases (an employee issue and a private placement both have an ex-date and a non-zero ratio). The class is a title-keyword classification of vendor text: it can miss a new wording (it then falls to `OTHER`, which fails safe, nothing is applied) and a title could contain a keyword for another reason; accuracy is a labelled task (3.6), not an assumption. A rights offer is not applied because the count changes only if the investor subscribes; no calculation of the investor's entitlement is attempted.

N2a itself displays no factor and no count. Any display of the factor, by N2b or N3, SHALL carry "calculated, check with your broker" (stated in the spec). Alternative considered: also show the multiplier now. Rejected: a multiplier on the count is the count line N2b is gated on.

"Share issues since purchase" use the same window as dividends (`purchase_date < exright_date <= last_bar`). `shares_as_of` is not used by N2a; N2b's arithmetic applies it.

### 7. Feed freshness states

`FeedSnapshot.status` is one of: `never_fetched` (`last_fetch` returns `None`: no log, no table, or no row for this ticker and `events`), `never_succeeded` (rows exist, `last_success_at` is `None`), or `fetched` (with `last_success_at`, and `latest_attempt_failed` when the latest row is `rate_limited` or `error`). Header of the DIVIDENDS block always carries it: `events last fetched <YYYY-MM-DD HH:MM> UTC`, plus `the latest attempt <time> failed` when applicable.

- `never_fetched` and `never_succeeded` replace the list, the Scheduled line and the incomplete flag with one sentence: no dividend or share issue can be listed or checked for this ticker, which is not the same as none found, plus the command (`python backend/scripts/snapshot_company_feed.py --tickers <T>`, "run by hand; this brief does not run it"). A ticker never passed to the snapshot (not among the 10 now in the log) reads this way.
- `fetched` with no qualifying events reads "none found". With a fetch, an old `last_success_at` is printed as is, with its age in days against the last bar; no staleness threshold is invented. The Scheduled line always ends "An announcement made after the last fetch is not shown."
- The brief SHALL NOT run, import, schedule or shell out to the snapshot. Enforced by the adapter's import rule (Decision 2) and a test that scans the brief package for `subprocess`, `os.system` and `snapshot`.

### 8. Window membership, shifted range, Scheduled

No trading calendar exists, so "in the window" for the next 5 sessions is `last_bar < exright_date <= last_bar + WINDOW_CALENDAR_DAYS` with `WINDOW_CALENDAR_DAYS = 7` (a Friday last bar gives Monday to the Friday after). A market holiday inside the window makes the real 5 sessions end later, so an ex-date up to a few days past the window is not flagged; it appears on the Scheduled line with its exact date. The window line prints the exact ex-date and says it is within 7 calendar days of the last bar. This only selects which feed dates to print; the range itself is still the model's 5-session band (Rule 1 is not changed, see Decision 12). Alternative considered: add a holiday table. Rejected: out of scope, and unverified for future years.

Shifted range: `(lo - D/1000, hi - D/1000)` where `lo`, `hi` are N1's display range in thousand VND and `D` is `value_per_share` in VND, rounded to two decimals like N1's range. Not shown (the sentence about the shift is replaced by "the shifted range is not shown") if the shifted lower end is not positive. Check: SAB at 07-23, issued 45.69 to 48.30, D = 3,000 gives 42.69 to 45.30; the recompute on adjusted history gave 42.75 to 45.19 (multiplicative instead of subtractive adjustment, so "about"). For a share issue in the window the price is adjusted by the issue; no number is shown (the lines say the board price is adjusted the same day and the range above does not apply from then). Two or more ex-dates in one window are each listed; the shifted range is computed only when exactly one cash dividend and no issue is in the window, otherwise "the range moves by more than one ex-date; not shown".

Scheduled: cash dividends and count-changing issues with `exright_date > last_bar` (ex-dates inside the window also appear here; N3 adds meetings), rights offers with an ex-date after the last bar, and "announced, no ex-date yet" bonus and stock-dividend rows (Decision 6). Ex-date, per-share amount or ratio, record date where given. Empty is "none found" only when the feed state is `fetched`. A rights offer whose ex-date is in the window also gets a window line saying to read the notice and that the board price may be adjusted the same day, so the range above may not apply from then (nothing computed).

### 9. The level note is a separate line (Rule 6, Rule 5)

For each level with entry date `e`, every cash dividend and count-changing issue (BONUS or STOCK_DIVIDEND, as in Decision 6) with `e < exright_date <= last_bar` produces one note line beneath the level's line (wording in Decision 13). It states a fact from the source, labelled by source, and says the brief does not change the level. It does not suggest moving or re-entering the level, never alters the investor's price or text, and never changes the "reached or not reached and the distance" wording of the level line. The note is a separate line, indented under the level, because Rule 6 and the `domain-rules` spec limit "the tool's own words **in that line**" to reached or not reached and the distance; the owner confirmed on 2026-10-12 that the note stays on its own indented line under the level (owner decision 1). The note depends on the adjustment status of that ex-date (Decision 16): when ADJUSTED it is as worded; when NOT_YET_ADJUSTED it adds that stored history is not yet adjusted for it; when UNCLEAR it adds that whether stored history is adjusted for it yet could not be told. Rights offers get no level note. The investor's verbatim rule text and the guard that strips it are N1's.

### 10. Dividend-aware THE WEEK JUST ENDED

The week is the last five stored sessions (`dates[-6]` start, `dates[-1]` end): exact, no calendar approximation. A cash dividend or count-changing issue (BONUS or STOCK_DIVIDEND) with `dates[-6] < exright_date <= dates[-1]` is "in the week" (rights offers are not: no price effect is calculated for them). What the block says depends on the number of such events and on the adjustment status of the ex-date (Decision 16).

**One event, status ADJUSTED (owner decision 3): one combined line that replaces N1's move line and its inside/outside sentence.** The board move comes first and the explanation is in the same sentence:

- Cash: `Board move: -7.7% (47.00 -> 43.40); about 3,000 VND of that is the dividend that went ex on 2026-07-28. Excluding the dividend: -1.3% (43.97 -> 43.40). Last week's range was ±2.8%: the move excluding the dividend was inside it.`
- Share issue: `Board move: -30.6% (50.42 -> 35.00); the price adjustment for the share issue (26.04 new shares per 100 held) that went ex on 2026-09-24 is about 20.7% of the price. Excluding the issue: -12.5% (40.00 -> 35.00). Last week's range was ±2.8%: the move excluding the issue was inside | outside it.`

Arithmetic, all from stored closes: `s` the stored close at `dates[-6]`, `c` the stored close at `dates[-1]`, `eve` the stored close on the last session before the ex-date, `D` the dividend in thousand VND, `r` the issue ratio.
- Raw prior close (the board price at `dates[-6]`): cash `s * (eve + D) / eve`, issue `s * (1 + r)`; rounded to two decimals for display, and the board percentage is computed from that displayed figure.
- Board move `= (c - raw prior close) / raw prior close`; excluding-dividend move `= (c - s) / s` (the stored, adjusted prior close); both simple percentages to one decimal (Rule 2), computed from the displayed prices.
- Worked check, SAB ex 2026-07-28 (stored closes 43.97 on 07-23, 43.60 on 07-27, 43.40 on 07-30; `D` 3.00): raw prior close `43.97 * 46.60 / 43.60 = 46.995`, shown 47.00; board move `(43.40 - 47.00) / 47.00 = -7.66%`, shown -7.7%; excluding the dividend `(43.40 - 43.97) / 43.97 = -1.30%`, shown -1.3%. The 2026-10-12 measurement (-7.65% from the unrounded 46.9955) agrees at one decimal. "About 3,000 VND of that" is the announced dividend; the start close moved by `s * D / eve = 3.03`, so "about" holds.
- Issue check: `s` 40.00, `c` 35.00, `r` 0.2604104: raw prior close `40.00 * 1.2604104 = 50.416`, shown 50.42; board move `(35.00 - 50.42) / 50.42 = -30.58%`, shown -30.6%; excluding the issue `(35.00 - 40.00) / 40.00 = -12.5%`; the adjustment is `r / (1 + r) = 20.7%` of the price.
- The range clause is percent only: the issued VND range is not comparable with a price after the ex-date (45.69 to 48.30 against a board close of 43.40 would read as outside while the move excluding the dividend is inside), so only `±<band>%` is printed. The inside or outside test is N1's: `|ln(c / s)| * 100 <= band_pct` on stored closes, which is exactly the move excluding the event.
- **Redaction (N1 review fix: the redacted copy carries no log-derived week text).** Everything in the combined line up to and including the footnote sentence comes from the feed and stored bars, so a `--redact` copy keeps it. The range clause (the issued band, the provisional-bar note, or the week-1 recomputed band) depends on what the issued log holds for the ticker, which shows how long it has been in the investor's briefs, so it appears only in the unredacted copy. A redacted copy of a one-event ADJUSTED week therefore reads `Board move: ...; about 3,000 VND of that is the dividend that went ex on 2026-07-28. Excluding the dividend: -1.3% (43.97 -> 43.40).` and the footnote sentence, and N1's `Move:` line and previous-range sentences are not printed in either form for that week.
- With no issued band (null band) the range clause is left out and N1's own sentence about the missing range stays. With no issued entry, the clause is the week-1 form (Decision 11): `Range recomputed today from prices up to <date>; not an issued range: ±<y>%: the move excluding the dividend was inside | outside it.`

**One event, status NOT_YET_ADJUSTED:** `History is not yet adjusted for the <ex-date> dividend; the stored move includes it.` (issue form: `...share issue; the stored move includes its effect on the price.`) after N1's move and range sentences, which are left as N1 prints them. The stored move already is the board move, so no second move is shown. **UNCLEAR:** it cannot be told whether the stored move includes it, no board move. **Two or more events:** the ex-dates with the status of each, no board move, N1's sentences unchanged. The calculation assumes the vendor's conventions, confirmed on several tickers (cash `(P - D) / P`: MWG 0.9868, SAB 0.9356; stock `1/(1 + r)`: FPT 0.9091); the board figure is only shown when the status is ADJUSTED, and labelled in the line by "about" and in the wording by "check your broker's figure" in the footnote sentence of Decision 13.

If the feed status is not `fetched`, the block says whether an ex-date fell in the week is not known and why.

### 11. Week-1 recompute fallback

When N1's issued-entry lookup finds no entry for the ticker, or entries but none with `as_of == dates[-6]` (N1's "first brief" and "no range was issued for the week" rows), `week_without_issue(...)` prints its line **after** N1's sentence; it does not replace it, so N1's own tests of those sentences stay valid. It does not apply when the matched entry has a null band (the issued brief chose to give no range; a recompute would contradict it). It uses the public pieces `sigma_daily_pct_from_closes`, `sigma_out_of_bounds`, `band_from_sigma` and `HORIZON_SESSIONS` (and the HAR model N1 already loaded): sigma from `closes[:-HORIZON_SESSIONS]` (prices up to `dates[-6]`), band `= band_from_sigma(sigma, model)`, move `= ln(c / s)` compared with the band in log space exactly as `_window_hits` does, displayed as a simple percentage. This composes public functions and does not import the private `_window_hits` or touch `volatility.py` (measured 2026-10-12: the recomputed band equals the issued band to two decimals for six ticker-date pairs). It needs 61 closes (`MIN_CLOSES`) before `dates[-6]`; otherwise "last week's range could not be recomputed". It shows percent only (no VND range), states "recomputed today from prices up to <date>; not an issued range", and is never written to the issued-brief log (it returns a string; N1's writer is not called, tested against a temporary log directory).

Comparison is **suppressed** (the band is shown, the move is shown, no inside or outside) when the feed status is not `fetched`, when two or more events fell in the week, or when the one event's status is not ADJUSTED, with the reason printed. When exactly one event fell in the week and its status is ADJUSTED, the comparison is made on the move excluding the event and printed in the combined line of Decision 10, with the board move first in the same sentence (owner decision 3). Reason for the earlier suppression: an adjusted-space comparison reports "inside" for a week where the broker shows a large fall (SAB 2026-07-23 to 07-30); the combined line removes that risk by showing the board move and the dividend before the verdict, and says "excluding the dividend" in the verdict itself.

The week-1 line (and the range clause of the combined line when it recomputes) is **unredacted-copy only**: whether it appears depends on the issued log having no entry, which N1's review fix keeps out of the redacted copy. It is derived from N1's `WeekFacts.kind` (`first` or `no_match`), not from a second read of the log, and a same-bar re-run prints it identically because N1's lookup ignores entries for the last bar.

Rule 4: the recompute adds no reliability figure and no "about 2 weeks in 3"; N1's coverage sentence stays with the next range.

### 16. Adjustment status: a runtime check on the stored bars, no vendor call

Stored history is rewritten by the vendor's adjustment some time after an ex-date, and only an upper bound on that lag is known (MWG: at most 3 sessions; no lower bound). So nothing in the brief assumes history is adjusted; it checks. For each cash dividend or count-changing issue with an ex-date on or before the last bar (from the feed), `adjustment_status(event, bars, model)` in a new pure module `adjustment_status.py` returns one of `ADJUSTED`, `NOT_YET_ADJUSTED`, `UNCLEAR`:

1. Find the stored bar dated the ex-date and the stored bar before it. Either missing, or an open or close that is not positive: `UNCLEAR`.
2. `P` = previous stored close, `O` = ex-bar stored open, observed gap `g = O / P - 1`.
3. Expected gap if history were **not** adjusted: cash `-D / P` (`D` in the stored price unit, thousand VND, `P` the stored previous close, which is the raw close under that hypothesis; the same arithmetic as the 2026-10-11 check: SAB 3.00 / 43.60 = 6.9%); stock `-r / (1 + r)`. The owner's note wrote cash as `-D / (P + D)`; that is the gap when `P` is already adjusted, so it is not used here (owner decision 2, 2026-10-12).
4. `UNCLEAR` when the expected gap is within `UNCLEAR_GAP_SIGMAS` (2.0) daily sigmas of the ticker (`sigma_daily_pct_from_closes` over the closes up to the previous bar, public, same model as the range; no sigma, or fewer than 61 closes, is `UNCLEAR`). Below that, an ordinary day's move can hide the gap. For the owner's 3% floor to hold, a sigma of 1.5% would be needed; SAB's typical daily sigma is near 1%.
5. Otherwise `NOT_YET_ADJUSTED` when `g <= e / 2` (`e` the expected gap, negative; the observed gap is nearer the unadjusted expectation than zero), else `ADJUSTED`.

Checks against stored data: SAB ex 2026-07-28: bars 43.60 close, 43.00 open, `g` = -1.4%, `e` = -6.9%, ADJUSTED. A synthetic unadjusted history (previous close 46.60, open 43.60, `g` -6.4%) is NOT_YET_ADJUSTED. A 500 VND dividend on a 22.9 price (`e` -2.2%) is UNCLEAR for a ticker with daily sigma 1.5%.

This needs stored opens, which N1's `read_recent_closes` does not return: the brief's `facts.py` reads the dates, opens and closes together from `ohlcv` (same query plus `open`; `volatility.py` is untouched) and `MarketFacts` carries the opens and a mapping from ex-date to status. The statuses feed the week note, the level notes and the explanation line of Decision 15. They are market-derived (computed from the feed and stored bars; no holding input), so a redacted copy keeps the week note and drops the level notes as before. Limits stated in the brief and here: a large market move on the ex-day can mimic or hide the gap, the check cannot see an event whose bar is not stored, and it says nothing about a lag it has no bar to read. It replaces the earlier dependence on an unverified vendor lag, but it is a heuristic check, not a guarantee.

## Risks / Trade-offs

- [`MAX_LAG_DAYS` rests on 10 tickers] A ticker with a longer lag could show a list as complete that is not. → 120 gives about 40% margin over the observed 85 (SAB; every other ticker 21 or fewer), the block always prints the oldest stored date, and the rule fails toward "may be incomplete".
- [The vendor may not have re-adjusted prices at the time of the run] → Not assumed: each ex-date's stored bars are checked (Decision 16) and the notes say adjusted, not yet adjusted or unclear. Residual: the check is a heuristic (a big move on the ex-day can fool it; an unclear small dividend says so) and the lag has only an upper bound.
- [Title keywords misclassify] A new vendor wording or a keyword in an unrelated title. → Unknown wordings fall to OTHER and are not applied; accuracy is counted on stored rows (task 3.6) and a title that matches two keywords is a test failure; a misread BONUS would show an issue line the investor can check against the broker, and nothing is calculated from it.
- [An unfetched or old feed is read as "none"] → Every feed line states the fetch time or that there was none; "none found" is printed only for a successful fetch; the snapshot command is printed. The snapshot clock is still manual, so the lines are only as fresh as the owner's last run.
- [Calendar-day window] A holiday week misses an ex-date one or two days past the window. → It still appears under Scheduled with its exact date.
- [Rights offers] Not applied; shown as "read the notice". → No entitlement is calculated.
- [Event codes and classes are inferred from titles] `ISS`, `DIV` and the five classes come from stored titles, not vendor documentation. → Tested against fixtures of every stored class; an unknown shape fails safe into OTHER or "none".
- [Fixtures] Stored rows are vendor data under a personal-use licence and the log is "not to be shared". → Fixtures copy dates and numbers only; an ISS title is only the keyword phrase that defines its class (for example "Cổ phiếu thưởng"), every other title is a placeholder; no real holding appears in any fixture.
- [The brief reads the log while a snapshot runs] SQLite read-only with a busy timeout; an unreadable log reads as never fetched, which the freshness line states.
- [N1's specs are not yet synced] Three of its requirements are MODIFIED here and must match its final text. → Task 1.1 re-diffed against N1's final text on 2026-10-12 (below); the spec scenarios are written against brief output, not function names.
