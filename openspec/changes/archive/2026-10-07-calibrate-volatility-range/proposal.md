## Why

The "±X% (5 sessions)" range the debate shows is a per-session sigma, not a 5-session range. `predict_volatility_range` returns `exp(pred) * 100` where `pred` is the log of the standard deviation of the *daily* log returns (`backend/app/ml/volatility.py:154-155`), with no scaling for the horizon, yet the panel, the Technical agent's prompt and the export all call it "5 sessions" (`DebatePanel.jsx:233`, `technical.py:98`, `export.py:102`). The 2026-10-06 post-pivot review (`docs/DISCUSSION_post_pivot_review.md`, Finding 1) measured the shipped band to contain the real 5-session move `|ln(close[t+5]/close[t])|` about 32% of the time (385,909 overlapping windows, 208 modelling tickers), and about 61-65% once multiplied by √5. It also found the output unbounded (the model is log-linear on raw features with no clip: 2818% for MTC), served to 599 tickers although trained on 208, and backed by a model artifact that is validated only by an in-sample correlation floor, written non-atomically, unversioned and unpickled on every request.

This change makes the range honest (a stated, measured coverage), bounded (an out-of-bounds status instead of an absurd number), and measurable (a per-ticker hit-rate computed from history, and a preserved script that reproduces the review's numbers).

These figures were measured in the 2026-10-06 review and have not been reproduced by the project; task 1 reproduces them before any later task relies on them.

## What Changes

- **Preserve the evidence first**: add `backend/scripts/evaluate_vol_range.py`, a read-only script that reproduces the review's coverage figures (as shipped, ×√5, time-split, outside the training universe, by year and by sigma quintile). It is the first task so every later claim is checkable.
- **Semantics**: `range_5s_pct = range_k × √5 × sigma_daily_pct`, labelled "typical 5-session move". `sigma_daily_pct` (the model's daily sigma in percent) stays an internal value and is never labelled "5 sessions". `range_k` is one global multiplier fitted out-of-time so that the band contains `|ln(close[t+5]/close[t])|` with a nominal coverage `range_coverage` of 0.68 ("about 2 in 3"). The coverage is stated wherever the band is shown.
- **Bounds**: a daily sigma above 7% (the HOSE daily price limit) is not served; the range endpoint answers `range_out_of_bounds` instead of clipping, and delisted or otherwise unfit tickers are refused by the shared `assess_eligibility` service rather than by new range-specific rules (the one exception: `/range` ignores the `indicators_missing` reason, because the range needs only closes).
- **New endpoint** `GET /tickers/{ticker}/range` returning `{ticker, as_of, status, reasons, sigma_daily_pct, range_5s_pct, range_k, range_coverage, range_hit_rate}`, where `range_hit_rate = {rate, n}` is the share of the ticker's last `n` five-session moves (non-overlapping windows over roughly the last year, `n` up to about 50) whose realised size stayed inside the band at that date, computed from at most 311 OHLCV closes by re-running the model per date.
- **Model artifact**: the pickle is replaced by `har_rv_model.json` (coefficients, `range_k`, `range_coverage`, version, `trained_at`, training universe, row counts, out-of-time validation results), written atomically and loaded once into memory (reloaded only when the file changes). `train_har_rv.py` validates out-of-time (expanding walk-forward by calendar year with a 5-session purge) instead of an in-sample correlation floor, and refuses to write an artifact that fails its gates.
- **Outside the training universe**: tickers that pass eligibility but are outside the 208-symbol calibration set are served with status `uncalibrated` and `range_coverage: null` (the label does not claim a coverage that was not measured for them).
- **Rename** (**BREAKING**, no deprecated alias): `volatility_range_pct` becomes `range_5s_pct` (plus `sigma_daily_pct`) in the debate result, `AgentPosition`, `POST /tickers/{ticker}/debate`, the export's Summary line, the panel's range line and the Technical agent's prompt. The debate result also carries `range_coverage` so the label can state it.
- Not in this change: a quantile-XGBoost challenger, per-ticker models, eligibility rules themselves, the Rule 4 ruling, label and disclaimer rewording (see Impact).

It supersedes the `**Volatility range**` template line and the "Volatility range is omitted when unavailable" scenario inside the existing requirement "Markdown export structure is NotebookLM-optimised" (see Impact for the reconciliation).
