## Goals / Non-Goals

**Goals:**
- Build Rail · Stage · Verdict as specified by the design at its widths, with the design's tokens in light and dark and a topbar theme toggle.
- One ticker search, in the topbar, working at every width, with the load-failure messages the app already has.
- A Rail that says, in text, why a ticker cannot be analysed, without per-row requests.
- A Stage header whose data date and age exist before a debate runs, range tabs, and a Debate matrix by agent and round.
- A single Verdict panel whose six states map to behaviour that already ships, keeping the runtime behaviours (server stage, elapsed time, kept result per ticker, error messages, `report_saved`).
- A layout that uses the whole viewport width, balanced, with no capped or centred column (Decision 15).
- Keyboard and screen-reader semantics stated and tested, contrast measured on the real CSS, no direction cue outside stance and verdict marks, and a page-load request budget that is tested.

**Non-Goals:**
- Watchlist curation (which tickers the Rail lists): pending; the Rail is the 208-symbol catalog plus session-searched symbols.
- New backend models, a new endpoint, authentication, a scheduler, multi-ticker verdicts, changes to the debate, the range, the eligibility rules or their thresholds.
- Any change to `CLAUDE.md`, `openspec/config.yaml`, `docs/DISCLAIMER.md` or the `debate-synthesiser` label table.
- Persisting anything but the chosen theme in the browser; the kept debate result stays in memory only.

## Decisions

### Decision 1: layout shell, tokens and theme

**Chosen.**

*Shell.* `App.jsx` renders, in DOM order: `Topbar` (`header`, `position: fixed`, height `--topbar-h` 52 px), `Rail` (`nav aria-label="Tickers"`), then `main` containing the Stage header, chart history tabs, chart card, `VerdictPanel` (`aside aria-label="Verdict"`), and the Debate matrix. A CSS grid places them: at 1144 px and up `[rail | main | verdict]` with the Verdict panel in the right column and sticky (`top: calc(var(--topbar-h) + var(--space-4))`, `max-height` to the viewport, its own scroll); the Rail is sticky the same way. Below 1144 px the grid is single-column and the Verdict panel sits between the chart and the Debate in the flow (Decision 2). `body` gets `padding-top: var(--topbar-h)` and `html` gets `scroll-padding-top: calc(var(--topbar-h) + var(--space-4))` so a focused element is never hidden under the fixed bar (WCAG 2.4.11, new in 2.2). Page padding is `--space-6` at 1440 px and up, `--space-4` below; `--space-4` between zones, `--space-5` between Stage sections (the design's own numbers).

*Tokens.* `styles/tokens.css` is rewritten from `tokens.json`: colour (`--surface-100/200/300`, `--line`, `--line-strong`, `--ink`, `--ink-muted`, `--accent`, `--on-accent`, `--up-ink`, `--up-bg`, `--down-ink`, `--down-bg`, `--candle-up`, `--candle-down`, `--band-fill`, `--warn-bg`, `--warn-line`, `--warn-ink`), spacing `--space-1..6` (4 to 32 px), radius `--radius-sm` 4 and `--radius-md` 8, layout `--topbar-h`, `--rail-w`, `--rail-w-min`, `--verdict-w`, `--chart-h`, and the type styles as classes (`kpi` 40/44 mono 700, `ticker` 28/32, `heading` 16/22 600, `body` 14/20, `small` 12/16, `label` 11/14 600 uppercase tracking 0.06 em, `num` 13/18 mono 500). All values are hex, so `lightweight-charts` and canvas read them unchanged (the band fill is `#rrggbbaa`; the library resolves colours through the browser, `lightweight-charts.development.mjs`, `_private__parseColor`, and the band primitive draws on a canvas, so 8-digit hex is accepted; to be confirmed in a browser, task 12.4). The old `--color-*`, `--space-2xs..2xl`, `--text-*`, `--radius-*` names are deleted in the same change, after each component's CSS is migrated; a final grep (task 11.4) proves none remain. *Fonts.* The two Google Fonts `<link>`s and the preconnects in `index.html:6-15` are removed and `ChartPanel.jsx:113`'s hard-coded IBM Plex Mono string becomes the mono stack. This follows the design (`tokens.json` has `fonts: []`), removes a render-blocking third-party request on every page load (each load told Google's servers the user's address and agent; worth stating under the organisation's data-handling note even though no ticker data was sent), and loses only glyph consistency across platforms.

*Theme.* Today there is no toggle (`tokens.css:3-4`) and dark mode follows the OS (`:85`); `index.css:9` declares `color-scheme: light dark`. New mechanism: the `data-theme` attribute on `<html>`. `tokens.css` defines light on `:root`, dark under `@media (prefers-color-scheme: dark) { :root:not([data-theme="light"]) {...} }` and again under `:root[data-theme="dark"] {...}`, with `color-scheme` set to match. `useTheme()` returns `{theme, toggle}`: the initial value is the stored choice else the OS value; `toggle` flips it, sets the attribute synchronously, then stores the choice in `localStorage` inside `try/catch` (storage can be blocked; the page must render without it). A small inline script in `index.html` applies a stored choice before first paint so a dark-theme user does not see a light flash. The toggle is a `<button aria-pressed>` labelled "Dark theme" in the topbar. With no stored choice the page keeps following the OS, including live changes (a `matchMedia` listener), which the chart does not do today.

*Chart theme.* `ChartPanel` subscribes to `useTheme().theme` and, on change, re-reads `readChartTheme()` (renamed to the new token names) and calls `chart.applyOptions` (background, text, grid, crosshair, scale borders), `candleSeries.applyOptions` (up/down colours), re-sets the volume data (the per-bar colour is in the data, `:276`) and calls a new `RangeBandPrimitive.setColor` that requests a redraw. Without this, toggling the theme would leave a light chart on a dark page.

**Alternatives considered.**
- *Keep the oklch tokens and map the design's hex onto them*: the design's contrast claims are computed on its hex values; keeping two vocabularies means re-proving them and the chart needs the converter forever (`lib/color.js`). `color.js` is left in place (its test and `setupTests.js` use it; it is idle once all tokens are hex, and can go in a later cleanup).
- *`prefers-color-scheme` only, no toggle*: the design puts a toggle in the topbar and the owner approved it.
- *Three-state toggle (system / light / dark)*: more control than the design shows; the two-state toggle with an OS default covers it, and "follow the OS again" is clearing storage.
- *Keep IBM Plex*: the design's tokens name system stacks; keeping the webfont is a one-line revert if the owner prefers it.
- *Alias layer (`--color-paper: var(--surface-100)`) kept permanently*: dual vocabularies that drift. Aliases may exist only while a component's CSS is mid-migration (sections 5 to 9) and are deleted in task 11.4.

### Decision 2: responsive behaviour and accessibility

**Modes.** One hook, `useLayoutMode()`, reads `matchMedia` (listener, no polling) and returns `wide` (>= 1440), `collapsed` (1144 to 1439), `drawer` (768 to 1143) or `phone` (< 768). CSS uses the same breakpoints in `@media (min-width: ...)`; a test reads the CSS text and asserts the numbers equal `lib/layout.js`'s constants (house style: `App.test.jsx:174-183` already reads CSS text). The hook decides **where a component renders**; CSS decides how it is laid out. Rendering in exactly one place matters for two cases: the range block (below), and the debate tabs.

| Mode | Rail | Verdict | Debate | Search |
| --- | --- | --- | --- | --- |
| `wide` | full, `--rail-w` 232, sticky | right column, `--verdict-w` 340, sticky | 3 columns by 2 rows | filters the Rail |
| `collapsed` | `--rail-w-min` 56, symbols only; expands as an overlay | right column | 3 columns | filters the (collapsed) Rail |
| `drawer` | hidden; a "Tickers" button in the topbar opens a drawer | full-width strip between chart and Debate: band and range check left, verdict, Agreement and stances middle, Key tension right | 3 columns | filters the drawer (typing opens it) |
| `phone` | none | range block first (above the chart), then chart (240 px), then verdict, Agreement, Key tension, Synthesis | 3 tabs (one per agent), Round 1 then Round 2 stacked inside | the combobox: matches listed under the input |

*Breakpoint (resolved 2026-10-07).* The first reading of the design put the collapse at 1100 px, where the Stage is 640 px (page padding `--space-4`, gutters `--space-4`, Rail 56, Verdict 340) and three columns with `--space-3` gaps give only 205 px, under the "at least 220 px" the design states. 220 px needs a 684 px Stage, a viewport of about 1144 px. The owner republished the design (version 10) with the Rail collapsing from **1144 px**, and the drawer layout covering 768 to 1143 px. Columns are then at least 220 px at 1144 (Stage 684), about 249 px at 1440 and about 237 px at 768. The constants, the hook, the spec and the tasks use 1144.

*Collapsed Rail overlay (accessibility).* Expanding "on hover or click" must work without a mouse and without hover: a toggle button at the top of the collapsed Rail (`aria-expanded`, `aria-controls`) pins it open; `:hover` and `:focus-within` also expand it (CSS only); Escape unpins it and returns focus to the toggle; selecting a row closes a pinned overlay. The overlay is positioned over the Stage (not pushing it), is **not modal** (no focus trap, the Stage is not made inert), and its rows' accessible names include symbol, loaded age and tag even while visually collapsed, so a screen-reader user hears the same thing at every width. The Refresh control is `opacity: 0` until hover or focus within the row (still in the tab order, never `display: none`), always visible on `(hover: none)`; WCAG 1.4.13 holds because the content is persistent while hovered or focused and dismissible with Escape.

*Drawer.* 768 to 1143 px: the "Tickers" topbar button has `aria-expanded` and `aria-controls`; the drawer is a non-modal disclosure region (`aria-label="Tickers"`), **not** `aria-modal`. A modal dialog would make the topbar search inert, but the design requires the one search to filter the drawer, so it must stay usable while the drawer is open. Typing a non-empty value opens the drawer without moving focus; Escape closes it and returns focus to the button; choosing a row closes it and returns focus to the button; a click on the scrim closes it. No slide animation (the design allows only a 120 ms colour change).

*Phone combobox.* The topbar input is the ticker picker: it carries `role="combobox"`, `aria-autocomplete="list"`, `aria-expanded`, `aria-controls` (the listbox) and `aria-activedescendant`; the listbox has `role="listbox"` and `role="option"` children (symbol, loaded age, tag; no direction cue). Down and Up move the active option, Enter selects it, Escape closes the list (a second Escape clears the input), Home and End are left to the text caret. For a symbol that is not in the list the listbox shows one option, "Load SYM", so a touch user has an explicit action (Enter does the same). The existing screen-reader count region (`TickerPanel.jsx:163`, "12 of 208 tickers") is kept. Outside `phone` mode the input has no combobox role (it filters a visible list rather than owning a popup). `App.test.jsx:142-156` asserts `queryByRole('combobox')` is absent; that test changes (Decision 11).

*Debate tabs (phone).* `role="tablist"` with `aria-label="Agents"`, three `role="tab"` (`aria-selected`, `aria-controls`, roving `tabindex`), Left/Right/Home/End move and activate (automatic activation is fine: the panels are local, nothing loads), `role="tabpanel"` with `aria-labelledby` and `tabindex="0"`, Round 1 and Round 2 stacked in each panel under `Round 1 · Initial positions` and `Round 2 · Responses` headings. An unavailable agent's tab says so in text.

*Range history control (not ARIA tabs).* The 3M / 1Y / All control changes the chart's visible window; it controls no panel, so it is a `role="group"` named "Chart history" of three buttons with `aria-pressed`, not a tablist. (The design calls them tabs; the word stays in the copy, the semantics are toggle buttons.)

*Everywhere.* Landmarks `header`, `nav`, `main`, `aside`; one `h1` (the selected ticker in the Stage header, or "No ticker selected"; the brand is not a heading); a 2 px solid `--accent` outline with a 2 px offset on every interactive element via `:focus-visible`; no information by colour alone; targets at least 44 px where the control is touch-primary (Refresh, tabs, toggle), never under 24 px (WCAG 2.5.8); `prefers-reduced-motion` honoured for the one remaining animation (the running spinner).

**Alternatives considered.**
- *CSS-only breakpoints, rendering all variants and hiding with `display: none`*: puts the hit-rate, Key tension and the disclaimer in the DOM twice, which breaks the "only surface" and single-disclaimer tests and doubles screen-reader output.
- *A modal drawer containing its own copy of the search*: violates "one search".
- *Hover-only collapsed Rail*: unreachable by keyboard and touch.
- *Reordering the phone layout with CSS `order`*: the focus order then differs from the visual order (WCAG 1.3.2 and 2.4.3). The hook-driven placement keeps DOM order equal to visual order in every mode.
- *Breakpoint 1100 as first read*: gave 205 px columns; superseded by the owner's 1144 px (2026-10-07).

### Decision 3: where the Rail's per-row eligibility tags come from

The row tag needs, per ticker, the reasons `assess_eligibility` would give. `GET /tickers` returns none. The page-load budget (Decision 12) is `GET /tickers` plus the selected ticker's requests; `retire-direction-model` removed a per-chip request burst (625 requests) and this must not bring one back.

**(a) Add `eligibility` to each catalog entry, computed in one batched pass.** New `assess_eligibility_many(tickers, now=None) -> dict[str, dict]` in `data_eligibility.py` reads the distinct session dates once, the latest features row and indicators for all tickers in one grouped read, the universe `listing_status` in one read, then per ticker one indexed `LIMIT 78` read of priced dates and one flags lookup. `assess_eligibility(ticker, now)` is rewritten as `assess_eligibility_many([ticker], now)[ticker]`, so the two are the same code and cannot diverge; an equivalence test over a synthetic database checks every reason. The entry gets `eligibility: {eligible, reasons, as_of, age_sessions}` (the function's own shape; about 90 bytes per entry, about 19 KB for 208), null for an unloaded ticker. Measured (table above): 0.19 s warm, 0.93 s cold for 208, equal results for all 208; against 8.7 to 19 s if the per-ticker function is called 208 times.

**(b) Fetch lazily per visible row.** Needs a per-ticker eligibility endpoint (none exists; `/range` returns reasons minus `indicators_missing` and no age, and computes a band) and a request per visible row, up to 208 (or a virtualised window of about 20 with request churn on every scroll and sort). It reintroduces the burst the previous change removed and fails the spec's "no per-ticker requests for tickers that are not selected".

**(c) Tags only after selection.** Zero cost, but then the Rail cannot say which tickers are usable: with 205 of 208 stale today, the user would have to click each ticker to learn that nearly all are refused. The design's row text ("Delisted", "Stale") would be empty until clicked.

**Recommendation: (a).** Page load stays one request; its payload and latency rise (about +19 KB, +0.2 to 0.9 s on this machine). `GET /tickers` is also refetched after every successful load or Refresh (the invalidation in `useLoadTicker.js:44-50` and the search mutation), so each Refresh pays the batched pass again; acceptable on a personal localhost app (Risk 2), with an in-process memo keyed on the newest `ohlcv` date and `now` rounded to the minute as the upgrade path (not built: no measured need).

Row tag text (the first reason in the fixed order, short form; the row's accessible name and `title` list all of them): `delisted` "Delisted", `insufficient_history` "Short history", `stale` "Stale", `near_gap` "Data gaps", `hard_quality_flag` "Quality flag", `indicators_missing` "No indicators". "Stale" is whatever the server says (`reasons` contains `stale`); the UI never compares an age with 3 (that cut-off is `MAX_AGE_SESSIONS`, provisional, `data_eligibility.py:22`; Rule 3 does not cover it and this change adds no threshold).

**Rail contents.** Unchanged from today's behaviour: catalog entries with `loaded: true` (all 208 now), plus symbols loaded through search this session that the catalog does not list. Watchlist curation stays pending. Searched-in rows have no catalog entry, so they show a "Loaded just now / Nm ago" age from the client clock at load time and no tag until selected (the Verdict panel then reads `/range`, Decision 5).

**Sort.** A native `<select aria-label="Sort tickers">` with `Symbol` (A to Z, the default) and `Last loaded` (most recently loaded first; never-loaded and searched-in-without-time last; ties by symbol). The catalog's server order (the nine legacy training tickers first, `api/tickers.py:111-113`) is ignored by the Rail, since it is a legacy marker and curation is pending. Direction of "Last loaded" is Open Question 6. Sort is session state, not persisted.

### Decision 4: one search in the topbar

**Chosen.** `TickerSearch` moves to the Topbar and loses its `Load` button, its `role="search"` form wrapper stays as the landmark (`<form role="search">`), and `TickerPanel`'s "Searched tickers" group, heading and its filter plumbing go.

- *Live filter.* Typing filters Rail rows by symbol, case-insensitive substring (as `TickerPanel.jsx:42-45`), placeholder "Search ticker", input upper-cased as today (`TickerSearch.jsx:239`), `maxLength` 12. The matching count is announced in the existing polite live region.
- *Enter on a symbol in the Rail* (a loaded catalog symbol or a searched-in one): select it, no request, clear the input so the Rail returns to the full list with the selected row scrolled into view (`TickerChip.jsx:52-54` logic, kept in `RailRow`). Today the value stays after a known-symbol Enter (`:197-201`) and the filter keeps hiding the other rows; clearing is a small behaviour change.
- *Enter on any other symbol*: `POST /tickers/{symbol}/load`; while it runs the input is disabled with `aria-busy` and a status line "Loading SYM..."; on `status: "ok"` add it to the searched-in rows if the refetched catalog does not list it, select it, clear the input. This keeps today's rule that a catalog symbol that is not yet loaded is also loaded first (`TickerPanel.test.jsx:146`).
- *Failures* use the messages that already exist (`LOAD_STATUS_MESSAGES`, `useLoadTicker.js:18-28`): `rate_limited` "Rate-limited by the data provider — try again in a moment.", `invalid_symbol` `"X" isn't a recognized ticker symbol.`, `no_data` `No data is available for "X" — retrying is unlikely to help.`, a non-2xx `ApiError` "Something went wrong loading this ticker — please try again.", a network failure "Network error — could not reach the server." (`TickerSearch.jsx:219-223`), each in a `role="alert"` line under the input, the typed value kept. The three statuses stay distinct from each other and from the two generic ones.
- *Empty result.* When the filter matches nothing, the Rail shows `No ticker in the Rail matches "X". Press Enter to load it.` (today's line says "press Load", `TickerPanel.jsx:126`).
- *Client-side validation*: none beyond `maxLength`; the server classifies malformed symbols as `invalid_symbol`, and a second rule in the client would be a second source of truth.
- *Phone*: Decision 2 (combobox, with an explicit "Load SYM" option).

### Decision 5: where the Stage header's data date and age come from

The header must say "As of D · N sessions old / current" and "Stale" before any debate runs (`data_age_sessions` exists only on the debate result today).

**Chosen: the catalog entry's `eligibility` (Decision 3) for the age and for "Stale", `/range`'s `as_of` (else the last `/history` row) for the date.** For a catalog ticker the age is `eligibility.age_sessions` and "Stale" is `reasons.includes('stale')`; both arrive with the page-load request and are refreshed whenever the catalog is (after Refresh). For a searched-in ticker the catalog has no entry: the header shows "As of D" with **no age claim** and takes "Stale" from `/range`'s `reasons` (which carries `stale`); the debate's own `data_age_sessions` appears in the Verdict data line once it runs. No number is ever invented for the missing case. A `useTickerContext(ticker)` hook merges these (and the last close from `/history`) so the header, the Verdict panel and the tests read one object.

**Alternatives considered.**
- *Add `data_age_sessions` (and all reasons) to `/range`.* It would give every ticker one source and delete the fallback above. It is a change to `volatility-range`, which this change may not edit; recorded as Open Question 5, with the wording of the one-line additive requirement if the owner wants it (`/range` already calls `assess_eligibility` at `range.py:78` and discards the age).
- *Add `as_of` and age to `/history`.* `ticker-history` says rows contain only OHLCV and the response is "pure OHLCV"; the envelope may grow but the capability is not this change's.
- *Compute the age in the browser from `/history`'s last date (`sessionDates.js` already counts weekdays).* The client cannot know market holidays or other tickers' stored sessions, so it would disagree with the server's `stale` decision (`data_eligibility.py:47-58`, which excludes holidays using other tickers' dates); two answers to "Stale" on one screen is worse than none. Rejected.
- *Only after the debate (today)*: violates the design ("every screen states the date") and the pre-run Insufficient-data state.

**Interplay of Stale and Insufficient data.** Stale never hides the chart. When `reasons` contains `stale` the header says "Stale" beside the date, the Rail row says "Stale", `/range` returns no band (`ineligible`), the chart draws candles only (shipped behaviour) and the Verdict panel is in the Insufficient-data state with the Refresh button (Decision 9). After a successful Refresh the invalidation (`useLoadTicker.js:44-50`) refetches the catalog, `/history` and `/range`, and all three places update with no page reload.

### Decision 6: the chart: range tabs, band, legend

**Range tabs (3M / 1Y / All).** No new request: `/history` always serves up to 750 rows (`api/tickers.py:14`). The control sets the visible logical range: 3M is the last 60 sessions (the existing `DEFAULT_VISIBLE_SESSIONS`, `ChartPanel.jsx:23`, which is already the opening view), 1Y the last 250, All `fitContent()`. Sessions are rows, never calendar days (Rule 1 sense: the horizon unit is the session). `setDefaultVisibleRange` becomes `setVisibleWindow(sessions)`; Reset zoom (`:306-312`) restores the **active** tab's window and auto-scale and pane split; a ticker change returns to 3M. A tab is disabled when the ticker has fewer rows than the tab's session count (3M needs 60, 1Y needs 250; today's catalog minimum is 306, so only a short searched-in ticker can disable one). **All** is a different case: the design's rule read literally ("fewer sessions than it needs", 750) would disable All for the 3 catalog tickers with 306 to 749 sessions, hiding history the app has. Chosen: All is disabled only when the ticker has no more rows than 1Y shows (<= 250), so it is never a duplicate of 1Y and never hides stored history. Open Question 4 records the literal reading. When the active tab is disabled for the new ticker, fall back to the widest enabled window; with fewer than 60 rows, `fitContent()` (the shipped fallback, `:236-239`).

**Band: shape (resolved 2026-10-07).** The first reading of the design drew a funnel from the last close plus a dotted flat line, which the shipped `dashboard-ui` requirement and `retire-direction-model` Decision 12 forbid (the wedge was rejected because it draws an envelope for t+1 to t+4 that no model produced and invites reading the band as a per-session path). The owner republished the design (version 10): **one vertical band, one session wide, at the t+5 position from `close x (1 - band)` to `close x (1 + band)`, dashed upper and lower bounds plus the band fill, the label `±X.XX%`, and no line or fan from the last close.** This equals the shipped shape, so the single-position band stays unchanged. The only chart work is the label and the colour (below). The candle series' default last-price line (`priceLineVisible` is not disabled at `ChartPanel.jsx:147-154`) may draw a horizontal line across the t+5 gap; task 12.4 checks in a browser and, if it does, disables it so nothing runs from the last close to the band.

**Band: colour (resolved 2026-10-07).** The design colours the bounds `--accent` with `--band-fill`; the shipped chart used the neutral ink. **Decision: restyle the bounds to `--accent`** (`RangeBandPrimitive.setColor`, constructed with `theme.accent`, fill `--band-fill`). Why: the accent is the one mark the design reserves for the projection (selection, focus, the Analyse button and the band bounds), so it identifies the band as the one forecast-like mark on the chart, and it is neither the up nor the down colour, so the shipped rule's intent (no direction hue, no arrow, symmetric) holds. The fill is decorative: the bounds and the label carry the meaning. Contrast: the bounds are non-text marks needing 3:1; `--accent` on `--surface-200` is 6.70 (light) and 7.22 (dark). A requirement replaces the neutral-ink one and task 7.9 restyles the bounds and checks the ratio on the real CSS.

**Band: label.** The primitive draws `±4.12%` (the same formatter as the Verdict kpi, two decimals) at the band; it is canvas text, so the chart section also gets an accessible text alternative (`role="img"` is wrong for an interactive chart; instead the `section` keeps its label and gains a visually hidden sentence "Last close 42.55; typical 5-session move ±4.12%" updated with the data), closing the gap `chart-panel.css:74-80` already notes.

**Legend (resolved 2026-10-07).** The OHLCV legend stays (`ChartPanel.jsx:384-411`) with Reset zoom. Its values are 12 px text coloured by up/down today (`chart-panel.css:117-123`). In the design `--candle-up` and `--candle-down` are "mark only; 3:1" and measure 4.11:1 (light, up) and 4.90:1 (light, down) on `--surface-200`, under the 4.5:1 text needs. The republished design settles it: **legend text uses `--ink`, with a small colour swatch in the candle colour beside the values; candle colours are never text colours.** This MODIFIES the legend requirement's colour scenario (the close >= open comparison, now shown by the swatch). Reset zoom and Refresh currently draw the **same glyph** (`ChartPanel.jsx:427-433` and `TickerChip.jsx:167-173`: identical path), so two different actions in one view look alike; Reset zoom gets a distinct path (task 7.6), both keep a 1.5 px stroke and an accessible name, per the design's icon rule.

**Chart size.** `min-height: var(--chart-h)` (440 px) growing to `56vh` at 1144 px and up, 240 px on phones (the design; today 26 rem and 18 rem at <= 480 px, `chart-panel.css:6-14,179-183`). The "no column more than one screen taller than the chart" rule is checked by hand at 1440 x 900 (a layout rule jsdom cannot test; task 12.5).

### Decision 7: the Debate matrix and the split of `DebatePanel`

**Chosen.** `DebatePanel` is dissolved into two components that share one `useDebateAnalysis(ticker)` call made once in the workspace and passed down as props (so both read the same run and kept result; the per-ticker `key` on the panel, `App.jsx:36`, is no longer needed because the three disclosure levels, `DebatePanel.jsx:424`, are gone):

- **`VerdictPanel`** (sticky, Decision 8): verdict badge, Agreement, three stance chips, Key tension, Synthesis, the data line, "Analysed HH:MM", the report-saved line, Re-analyse, the disclaimer and "About this analysis", plus everything about running and failing.
- **`DebateMatrix`** (Stage, below the chart): three agent columns (Technical Signal, News Context, Macro) by two rows (`Round 1 · Initial positions`, `Round 2 · Responses`); each cell is one card with the agent label, the stance mark (arrow and word) and the reasoning bullets. Cards are aligned by row. Text is clamped to five lines of `body` (`max-height: calc(5 * 20px)`, `overflow: hidden`; **not** `-webkit-line-clamp`, because `display: -webkit-box` on a `<ul>` drops list semantics in Safari/VoiceOver) with a "Show more" button (`aria-expanded`, `aria-controls`) shown only when the text overflows (measured with `scrollHeight > clientHeight` in a layout effect and on resize; jsdom reports 0, so unit tests stub the two properties). An agent in `agents_degraded` gets a dashed `--line-strong` card reading "Unavailable — did not vote" with the plain-language reason from `DEGRADED_REASON_TEXT` (`DebatePanel.jsx:35-40`); for `round2_failed` the Round 1 cell shows the position normally and the Round 2 cell is the Unavailable card with the "Round 2 failed; its Round 1 position is shown but not counted." reason (the backend copies Round 1 into Round 2 with that marker, `engine.py:228-234`, so repeating the bullets would show them twice). The matrix says "Reasoning is written by a language model." (the existing `LM_NOTE`, Rule 5) above the grid and shows the inline disclaimer line under its heading (Rule 6: agent reasoning is displayed here, outside the Verdict panel). Before a result it shows a one-line prompt ("Run Analyse to see each agent's Round 1 and Round 2 positions.") under its heading; while running, six skeleton cells (`--surface-300`, `aria-hidden`); for a refusal result (no agents ran: `round1` and `round2` empty, `engine.py:85-100`) it says no debate was run and why; for an abstention after agents ran (fewer than two live) it shows the cards with the Unavailable ones. Never one scrolling text column (the design's rule); below 768 px, tabs (Decision 2).

**What keeps its behaviour, unchanged.** `describeFailure` and `FailureNotice` (`:53-83`, `:390-403`), `RunningState` and the server-reported stage and client elapsed seconds (`:379-388`), `useDebateAnalysis` (kept result per ticker, switching tickers neither cancels a run nor discards a result, a failed run keeps the old result under the error), the 200 s client limit, the `report_saved && report_file` line, `Inline` (Markdown bold rendered as `<strong>`, never as HTML, `:132-137`), `agreementText` (`:116-128`), `dataDateText` (`:145-149`), and the inline and full disclaimer strings in `lib/disclaimer.js`.

**What is removed.** The three disclosure levels and their two toggles ("Show reasoning", "Full debate", `:335-358`), the Level 3 transcript layout (`:287-312`, `Round 1 — Initial Positions` headings become `Round 1 · Initial positions`), and the debate panel's own range line (`:216-221,330-332`): the typical move is now the Verdict panel's first element (Decision 8), and keeping the line would show the band twice.

**Alternatives considered.** *Keep `DebatePanel` as one component and move it into the Stage*: contradicts the design (Verdict is sticky and holds the verdict, Key tension and Synthesis; the Stage holds the cards). *Duplicate the result into both places from two hook instances*: a second `useMutation` observer in the matrix for no reason. *A React context for the debate state*: one prop pair is enough for two consumers.

### Decision 10: direction marks, colour and error text

- **Stance chips and the verdict badge** use `--up-ink` on `--up-bg` for bullish, `--down-ink` on `--down-bg` for bearish, `--ink` on `--surface-300` for Observe and Split, `--ink-muted` on `--surface-300` with a dashed `--line-strong` border for Insufficient data (the design's table). Shipped differs on two counts: text is always `--color-ink` with tint reserved for the strong variants (`debate-panel.css:110-112,127-131`), chosen so "a solid green/red pill never reads as a buy/sell button". - **Warn colours are Key tension's alone.** Shipped uses them on the Split badge (`debate-panel.css:132`), the Insufficient border (`:133`), the degraded chip and card (`:168,209`) and Key tension (`:238-239`); the first four move to `--surface-300` / dashed `--line-strong`.
- **Errors and notices carry no hue.** The design has no error colour and reserves `--down-ink` for bearish; a red "Analysis failed" would look like a bearish cue. - **No direction cue on a Rail row**, no status dot, no signed return, no projected point, no "Confidence", no `▲ ▼`. Arrows appear only on stance chips, verdict badge and agent cards. Checked by the scan in Decision 11.
- **Contrast** (design claims, recomputed from `tokens.json` with the WCAG 2 formula in both themes): every claimed pair holds. Light: ink on surface-100/200/300 16.75/18.13/15.42; ink-muted 7.08/7.67/6.52; line-strong on surface-100/200 3.69/4.00 (3:1 needed); accent on surface-100/200 6.19/6.70; on-accent on accent 6.70; up-ink on surface-200/up-bg 6.55/5.68; down-ink 6.64/5.56; candle-up/down on surface-200 4.11/4.90 (3:1 needed); warn-ink on warn-bg 10.93; warn-line on warn-bg 4.46 as first published (see caveat 1). The owner republished the design (version 10) with light `--warn-line` `#a05a00`, which gives 4.80:1 on `#fff3d1` (recomputed here; dark `#e3a22f` on `#2e2510` is 6.83:1, the owner states 6.8), so the 11 px Key tension label in `--warn-line` passes 4.5:1 in both themes and `--warn-ink` stays the body text. `tokens.css` copies the republished values (task 5.1 re-reads `tokens.json`). (2) `--up-ink` and `--down-ink` have almost the same lightness (relative luminance 0.110 and 0.108 light, 0.433 and 0.401 dark): for the common colour-vision deficiencies they are indistinguishable by lightness, which is exactly why the arrow and the word are mandatory (the design says so). ### Decision 15: the layout uses the full viewport width (owner requirement, design version 11, 2026-10-07)

**Chosen.** No `max-width` anywhere on the shell or a zone, equal left and right page padding (`--space-6` from 1440 px, `--space-4` below), Rail 232 px and Verdict 340 px fixed by token, and the Stage `minmax(0, 1fr)`. Stage widths follow from the arithmetic (page padding 2 x 32, gutters 2 x 16): 772 px at 1440, 1252 at 1920, 1892 at 2560 (the Debate columns are then 249, 409 and 623 px, equal by `repeat(3, minmax(0, 1fr))`). A zone shorter than its row is `align-self: start` (top-aligned) or stretched, never `margin: auto`. The current tree has no cap to remove (`App.css:1-11` comments that an earlier `max-width: 72rem; margin: 0 auto` was already removed, and `App.test.jsx:174` asserts it); the only `max-width` rules left are a 26 rem message width inside the chart overlay (`chart-panel.css:148`) and media queries, neither a layout cap. Task 5.6 searches again for any cap or auto margin the new shell might introduce.

**Alternative rejected: a centred `max-width` (for example 1600 px).** It keeps line lengths and the chart's candle count sane on ultra-wide screens, but leaves blank margins on both sides, which is exactly what the owner ruled out; the chart and cards are meant to grow.

**How the chart plot fills the card.**
- `createChart` already uses `autoSize: true` (`ChartPanel.jsx:144`), so the canvas follows the card through the library's own resize observer. What does not follow is the visible range: lightweight-charts keeps the bar spacing on resize, so a wider card would show more sessions and a narrower one fewer. The history window is therefore **re-applied** (`setVisibleLogicalRange`) from a `ResizeObserver` on the card (one animation frame after a size change) unless the user has zoomed or panned since the component last set a range (tracked by comparing `subscribeVisibleLogicalRangeChange` events with the range last applied); Reset zoom and a tab change always re-apply.
- **Candles per tab do not depend on width**: 3M is always 60 sessions, 1Y about 250, All every served row (at most 750), because the tabs are defined in sessions (Rule 1's unit). Width changes the bar spacing instead: about 21 px per session at 3M in a 1500 px plot, about 5 px on a 340 px phone plot; 1Y and All get narrower bars. Alternative rejected: show more sessions on wider screens (the tab names would stop meaning what they say).
- **The t+5 band and its label.** The band sits at logical index `count - 1 + 5` (`sessionDates.js`, `ChartPanel.jsx:354`) and is one bar wide, so with the right margin currently fixed at 5 slots (`RIGHT_MARGIN_SESSIONS`, `:24`) its right half and its label would overrun the plot's right edge. The visible range's right end becomes `count - 1 + 5 + extra`, where `extra = max(1, ceil((labelPx + gapPx) / barSpacing) )` slots keep half a bar plus the label width inside the plot (labelPx measured with `measureText` for the `±X.XX%` string; barSpacing read from `timeScale().options()` after the left edge is set). The label is drawn to the left of the band's upper bound when there is not room on its right, so it never leaves the card. The plot's left edge is the first session of the window.
- The price scale keeps `minimumWidth: 82` (`:141`) and the volume pane shares the time axis, so volume bars span the same width.

**Tests (no layout in jsdom).** Three layers: (1) CSS-text tests assert no `max-width`/auto margin on the shell and zones, equal inline padding, fixed Rail and Verdict widths from tokens, `minmax(0, 1fr)` for the Stage and the Debate grid; (2) a pure `zoneWidths(viewport)` helper in the test (reading the token values from `tokens.css`) asserts the 1440, 1920 and 2560 px arithmetic above, that the zones plus gutters plus paddings equal the viewport, and that the three Debate columns are equal; (3) `ChartPanel` tests stub the card's size (a `ResizeObserver` mock and `clientWidth`) and the chart's `barSpacing`, and assert the same 60-session window is applied at 772, 1252 and 1892 px, re-applied on a resize, not re-applied after a user zoom, and that the right edge leaves room for the label. The pixels are checked by eye at 1440, 1920 and 2560 px in both themes (task 12.8).

## Risks / Trade-offs

- **Almost every ticker is Stale today (205 of 208), so the new layout mostly shows refusals.** The Rail will read "Stale" on nearly every row and the panel will offer Refresh instead of Analyse. → Intended: it is the truth the guards produce. Mitigate: Refresh is one click in the row and in the panel; a refreshed ticker flips to a full state with no reload. A bulk refresh is out of scope (a scheduler is a non-goal).
- **Catalog payload and latency grow** (about +19 KB; +0.2 to 0.9 s) and every load or Refresh recomputes all 208 reasons. → Measured; acceptable on localhost; the memo upgrade path is written down (Decision 3). If a later measurement on a slower disk shows more, compute only the entries for tickers that changed.
- **Eligibility in the catalog can age while the tab stays open** (`now` is evaluated at request time; the app does not refetch on focus, by design, `queryClient.js:9-13`; "Loaded Nd ago" drifts the same way). → A stale tab can show "current" for a ticker that has since become stale; Refresh or a reload recomputes. Documented; not fixed.
- **Two sources for the age** (catalog for catalog tickers, nothing for searched-in ones). → The header never invents a number; Open Question 5 offers the one-line `/range` addition that removes the asymmetry.
- **Chart behaviour cannot be unit-tested in jsdom** (canvas, primitive pixels, theme re-colour, tab windows' visual result, the label text). → Tests assert the inputs (visible logical range, `applyOptions` calls, primitive colour and label strings); the pixels are checked by hand in a browser (task 12.4) and the result recorded in this file.
- **A hook-driven layout flashes on first paint** if `matchMedia` is read after render. → Read it synchronously in the initial state; CSS media queries lay out the page before React hydrates anything, and the hook only chooses placement of the range block, debate tabs and combobox role.
- **Moving the Verdict panel's content to three places** (right column, strip, phone order) is the likeliest source of duplicated DOM. → One component per block, rendered once; tests count occurrences of the hit-rate, Key tension and disclaimer text at all four modes.
- **Rule 6 reach.** The design puts the disclaimer only in the Verdict panel, but agent reasoning is displayed in the Stage matrix. → The matrix repeats the inline line (it cannot be hidden), and in `drawer` mode the strip carries the panel's disclaimer.
- **Removing Google Fonts changes the typography on every platform.** → Reversible in one line; the design asks for it.
- **Wide screens (2560 px) give 20 px candles at 3M and a 1892 px Stage with 623 px Debate cards, with long lines of text.** → Accepted by the owner's requirement; cards clamp to five lines, and the clamp is by lines, not width.
- **Scope**: this is a rewrite of five components and about six test files. → Sequenced so each step is green; no backend change except one additive field.

## Migration Plan

No data migration and no schema change. `GET /tickers` gains one additive field, so an old frontend keeps working against the new backend and a new frontend degrades (no tags) against an old backend: the Rail treats a missing `eligibility` as unknown (no tag, no age), which keeps a half-deployed state usable. `localStorage` gains one key (the theme choice), written only on toggle. Rollback: revert the frontend commit(s); the backend field is harmless to leave. The removed components, their CSS and tests are recoverable from git; nothing outside `frontend/src`, `frontend/index.html`, `frontend/package.json` (the icon dependency), `backend/app/api/tickers.py`, `backend/app/services/data_eligibility.py` and their tests is touched.
