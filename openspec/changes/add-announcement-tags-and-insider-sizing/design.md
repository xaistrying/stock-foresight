## Goals / Non-Goals

**Goals:**
- A COMPANY block per held ticker that separates "needs a look" from "for information", with tags the reader can trust and a visible fallback for everything else.
- A trade line that states what the record says and no more: who, which direction, how many, which window, and where the window stands against the brief's date.
- A size and benchmark whose basis is stated, with the fallback path as first-class as the sized path.
- Provenance and safety: third-party text labelled, bounded and sanitised; no tool-originated buy, sell or hold word.

**Non-Goals:**
- Dividend, ex-date and share-issue lines for the investor's position, totals, share count after an issue (N2a, N2b).
- The individual, institution or related-person class (omitted, Decision 5).
- Any model-written text, summary or translation; any verdict; any change to a domain rule; any frontend.
- Claiming that sizing helps. Its effect on real investors is untested.

## Decisions

### 1. Layout: pure modules, one adapter, one new vendor module

New modules in `backend/app/services/brief/`, none importing `vnstock` and none containing the text `company_feed` (the isolation test greps for it): `announcements.py` (pure: classification, membership), `insider.py` (pure: title parsing, window state, size, benchmark), `third_party_text.py` (pure: sanitiser), `share_cache.py` (stdlib only: the cache file), `wording_company.py` (every fixed COMPANY sentence as a constant, so N1's verb guard scans it as it scans `wording.py`) and `sections_company.py` (the section function; `compose.py` gets one entry).

The brief's only file that references the company feed stays N2a's `feed_source.py`. This change adds to it, and does **not** add a title to N2a's `Event` (N2a's scenario says an event carries no stored text): a separate frozen `Announcement` type (kind, item date, first-seen date, `from_first_fetch`, event code, the sanitiser's input title, `action_type_en`, `start_date`, `end_date`, `exright_date`, `issue_date`, `listing_date`, `record_date`, `exercise_ratio`), `read_announcements(ticker)` built from `latest_items(ticker, "news")` and `latest_items(ticker, "events")`, and per-kind source health from `last_fetch(ticker, "news")` and `last_fetch(ticker, "events")`. It reads through the same two store helpers and nothing else, so the amended isolation test's "store module only" check still holds. The source name, source link and author fields of news items are not carried.

The vendor-facing share count code lives **outside** the brief package, in `backend/app/services/share_count/fetch.py`, so the brief package stays free of `vnstock`. It is the only new `vnstock` importer, calls `app.vnstock_guard.install()` before the import (enforced by `test_every_vnstock_importer_installs_the_guard_first`), is the only code that talks to the vendor for a share count, and, like every file outside the adapter, must not contain the text `company_feed` (its ticker pattern is written out, with no comment naming that package). The thin script wires: adapter data, then (only if needed) cache then fetch, then the pure section functions. `--redact` needs no change: nothing in the COMPANY block is derived from holdings and tickers are kept.

Alternative considered: put the fetch in `feed_source.py`. Rejected: it would pull `vnstock` into the adapter and make the one file allowed to touch the feed also a vendor importer.

### 2. Classification: record first, keywords only for company filings, nothing is "routine"

Tag set, in the order the block uses it: insider or major-shareholder trade; share issue or capital change; dividend; shareholder meeting; results; personnel or disclosure officer; and **"Other announcement, not classified; the title gives no amount"**. There is no routine, minor or administrative tag. Every item carries a basis label, "(event record)" or "(title keyword)", so the reader can see how it was tagged (Rule 5).

- **From the event record** (event code, no keywords): `DDIND`, `DDINS`, `DDRP` to insider trade; `ISS` to share issue or capital change; `AIS` (additional listing, title "Niêm yết bổ sung ...") to share issue or capital change; `DIV` to dividend; `AGME`, `EGME` to meeting. Any other code (`OTHE`, `SUSP`, `AGMR`, `MA`, `MOVE`, `NLIS`, `RETU`, unknown) is unclassified. The mapping covers only the codes seen in stored rows. The library names `AIS` among "other events", so the `AIS` mapping rests on three stored titles and is checked by the code-by-title cross-tab in task 2.3.
- **From a title keyword** (news only, and only when the title starts with `<TICKER>:`, a company filing): classes for share issue or capital change, dividend, meeting, results, personnel. Precedence: any match on the share issue or capital change class wins (over-flagging is the safer error); otherwise exactly one other matching class is used; two or more other classes match means unclassified. `Nghị quyết HĐQT` alone, bond issues and bond buy-backs ("trái phiếu"), penalties and transfer-restriction notices are never matched. The keyword lists are data in one module, with Vietnamese text and no stemming.
- **Press items** (titles not starting with `<TICKER>:`) may concern another company, so they are never classified: "Press item (may concern another company; not classified)", always in "For information".
- **Accuracy gate.** Only coverage (97 of 100 titles) was checked before, not accuracy. Keyword classes **ship disabled** (`ENABLED_KEYWORD_CLASSES` is empty in code; functions take the set as a parameter so tests enable them). Task 2 runs a read-only script over the stored titles, the owner labels a sample, and a class is enabled only if every title it claims is correctly labelled (no wrong assignment) and at least 3 titles carry it; otherwise its titles stay unclassified. Counts per class (claimed, correct, missed from the unmatched pile) are recorded in this file at apply time, **counts only, no titles**, because the log is marked not to be shared. A missed capital-change title is the dangerous error, so the script also lists unclassified titles that contain a share or capital word for the owner to read.
- "Needs a look" holds exactly two tags: insider trade and share issue or capital change, the same two the footer names. Everything else is "For information". Two exceptions inside the capital-change tag (owner decisions 2026-10-12): an issue event below `ISSUE_MATERIAL_RATIO` (1%) is not listed individually but counted in one quiet summary line (Decision 12), and an `AIS` additional-listing event goes to "For information" with the same tag, because it only lists shares from an earlier issue and has no ratio to test (the stored ones include small employee listings).

Alternative considered: classify everything including press, and a "routine" bucket for board resolutions and notices. Rejected by the evidence in Appendix F: the bucket caught 43 of 100 titles and included resolutions that carried real transactions and a tax penalty notice.

### 3. Which items are listed ("since the last brief")

An item is listed when its date (`published_at`) is after the last-bar date `L` of the previous issued brief for that ticker (N1's log), **or** it was first seen after `L` and did not arrive in the ticker's first fetch (`from_first_fetch` false), so a late snapshot does not hide it. With no previous brief the lookback is 14 calendar days before the current last bar (`FIRST_BRIEF_LOOKBACK_DAYS`; non-price constant), and the block says so. An item can appear in two consecutive briefs when it was first seen between `L` and the issue time; that is accepted over missing it.

An insider trade whose window has not ended is also listed when it is not new, marked "listed again: window still open", because a window can outlast the brief that first showed it and silence would read as absence. "Needs a look" and "For information" each show the newest 10 and say how many more exist (`NEEDS_ITEMS_MAX`, `INFO_ITEMS_MAX`); the triggers line counts every listed item (review fix 6).

"Scheduled" moves into the COMPANY block (where the v5.3 template has it; N2a prints it inside DIVIDENDS and says N3 may move it). It is one line in one place: N2a's scheduled ex-dates and count-changing issues (from its `scheduled_events`) plus meeting events (`AGME`, `EGME`) whose `record_date`, `exright_date` or `issue_date` falls after the last bar and within `WINDOW_CALENDAR_DAYS` (N2a's 7) days. Each meeting date is printed with the source's own field name and the line **does not say** which is the meeting date: in one stored example the issue date matches the meeting but that is a single case. N3 removes the Scheduled line from the DIVIDENDS block so the same dates are not printed twice, and keeps N2a's closing sentence "An announcement made after the last fetch is not shown." "none found" is printed only when the source has answered; otherwise "not checked" (N2a's never-fetched wording).

### 4. Source-health line

Per ticker, from `last_fetch` and the newest `published_at` of the stored items, for news and for events separately:

- Answered: "announcement source answered <date>; <n> items returned; newest <date>" (news), then "corporate events: answered <date>; <n> returned; newest <date>". `<date>` is `last_success_at`; `<n>` is `items_returned` of the latest successful fetch. When `n` equals the source's per-call limit (50; the adapter holds the constant and a test ties it to `fetch.VENDOR_ITEM_CAP`) the line adds "(the source's limit per call; older items are not retrievable)".
- Answered, newest item old: "newest <date>, <k> days before this brief; nothing newer was returned". No threshold decides whether this is "stale"; the age is printed. This is the reading that left 0 of 20 simulated readers doubting the source (Appendix G).
- Answered before the brief: the age of the last answer against the last bar is always printed, with N2a's sentence "An announcement made after the last fetch is not shown." No staleness threshold is applied (N2a's rule too), and the snapshot command comes from N2a's `snapshot_command`. The brief never runs it.
- Latest attempt failed (`error`, `rate_limited`): "last attempt <date> failed (<error class>); last answer <date>".
- Never fetched or never succeeded (N2a's statuses; no `last_fetch`, or no successful row): "announcement source never fetched for <TICKER>; announcements not checked" (or "no successful fetch yet"), and the three sections read "not checked", never "none". The news and event kinds can differ (the events status comes from N2a's snapshot, the news status from the same helper on kind `news`). "none found in what the source returned" is used only after a successful fetch.

### 5. Trade line, window state, quantity, class

From the title with `^(?P<name>.+) - Đăng k[íý] (?P<act>Mua|Bán)(?: (?P<qty>[\d,]+))? (?P<tk>[A-Z0-9]+)$` (53 of 53 stored titles match). The name is the text before the last " - Đăng kí". The direction shown comes from `action_type_en` (`Buy` or `Sell`) and is used only if it agrees with Mua or Bán and the ticker matches; otherwise the line shows the sanitised verbatim title and "direction or quantity could not be read from the title".

The window comes from `start_date` and `end_date`, compared with the brief's last-bar date `as_of`:

- `start > as_of`: status "not started".
- `start <= as_of <= end`: status "under way", then "the record does not say how much has been carried out".
- `end < as_of`: status "ended", then "the record does not say whether it was carried out".
- Missing dates: "window not given in the record".

The line reads: `“<name>” filed a notice of a sale of <qty> <TICKER> shares (window <start> to <end>; status: not started | under way | ended)`, or "a purchase of" (owner decision 2026-10-12: no buy, sell or hold word appears in tool text; the v5.3 "registered to SELL" frame and "planned, not yet executed" are dropped). "Sale" and "purchase" come from a closed set mapped from the vendor's action field (`Sell` and `Buy`); an unreadable direction gives "filed a notice (direction or quantity could not be read from the title)". The name is third-party text inside the sanitiser's quotes.

The three states exist because 46 of 53 stored records appear after their window ended, so a bare "planned" would be false for most. "The window runs <n> weeks; this brief covers one." is added when `end > as_of + 7 days`, with `n = ceil((end - start + 1 days) / 7)`. Each item of these classes ends with "The usual range is built from past prices only. It does not account for this announcement, so the real swing could be larger."

A missing quantity (12 of 53) gives "filed a notice of a sale of <TICKER> shares (quantity not stated in the title ...)" and the fallback checklist. **The event-code class is omitted** from the line: the library documents the three codes as one group, the split is an inference from names, and v5.3 allowed omission. Task 3.4 looks once for a vendor definition and records the result; the class stays omitted in this change either way.

### 6. Rule 6: one exemption, third-party quoted text

Owner decision 2026-10-12: the closed-form "registered to SELL|BUY" frame, its guard exemption and the `RENDER_FILING_FRAME` switch are **removed**. Tool text never contains buy, sell or hold; a registered trade is written with the nouns "sale" and "purchase" (Decision 5), which the guard's `\b(buy|sell|hold)\b` pattern does not match. The footer's "a registered sale or purchase by a major shareholder or insider" stays. No rule text is edited.

The guard over the brief's tool-originated text keeps N1's investor-string removal and gains **one** exemption: **third-party spans**, meaning text inside U+201C and U+201D quotes, produced only by `third_party_text.third_party()`, which removes those two characters from its input so a source cannot close its own span. The guard strips each span before scanning. Every constant tool string in the brief package contains neither character (a test enforces it), and the COMPANY section headers say "(third-party text)" so each span is labelled (Rule 5).

Guard tests (simple): a tool string with "SELL", "buy" or "hold" fails (the guard is N1's whole-word match, so an inflected form such as "selling" is not caught by it; the new constants avoid those forms by hand and a test scans them); the same words inside a sanitiser span pass; the same words in text quoted with other quote characters fail; a span closed early by an embedded U+201D is closed by the sanitiser, so what follows is scanned; "HOLDINGS" passes; a rendered trade line contains no direction word outside its quoted name.

### 7. Third-party text

Titles and names are shown in their original language. `third_party(text, limit)` applies the existing `_clean` (reused from `news_feeds`, as `normalise.py` does), then: removes U+201C and U+201D; replaces `|` with `/`, a backtick with an apostrophe, `<` and `>` with `‹` and `›`, `[` and `]` with `(` and `)`; replaces any `http://` or `https://` run with "(link removed)"; collapses whitespace; caps at 200 characters for titles and 120 for names (stored titles go to 500, so a cap with "…" is applied on display). This neutralises the three leaks the discussion doc's "Risk and privacy" section names (unclosed tags, markdown links and table pipes), which `_clean` and the existing prompt `fence` leave intact. Emphasis characters (`*`, `_`, `#`) are left alone: they change appearance, not structure. No model sees this text.

### 8. Shares outstanding

- **Source**: `Company(source="vci", symbol=S).ratio_summary()` (from `vnstock import Company`; confirmed by live probe 2026-10-12, see "Verified column names" below). Take the latest row **with `ratio_type == "RATIO_TTM"`** by (`year_report`, `quarter`), both integers; **never sort by `year`, which is a string**, and never sort the unfiltered frame (the 8 annual `RATIO_YEAR` rows carry `quarter = 5` and would win). The count is column `number_of_shares_mkt_cap` (int64). It is cross-checked against the four `issue_share` columns of `overview()`, **read by position** (the names are duplicated, so a label lookup returns a frame). The count is used only when it equals **every** one of the four values. A missing `overview()` field, a zero, NaN or non-integer count, no `RATIO_TTM` row, or any difference means "cannot size". The module keeps `fetch.py`'s convention of no URL, no `requests` and no private method.
- **The latest row is live, not "as of the quarter"**: VPB's 2026-Q2 TTM row already showed 10,000,000,000 shares after the 2026-09-24 stock dividend. The line therefore never says "as of <quarter>"; it says "latest-quarter row <year>-Q<q>, fetched <date>".
- **Rate limit**: the call catches `SystemExit`, passes it to `bulk_ingestion._is_rate_limit_exit`, and turns vnai's limiter into an ordinary `ShareCountUnavailable`, as `company_feed/fetch.py` does; any other `SystemExit` passes through. No wait and no retry (the script is interactive): the brief degrades to the cached value or the fallback. The ticker is validated against `[A-Z0-9]{1,12}` before use (copied, not imported, because the isolation test restricts imports of `company_feed`).
- **Fetch policy**: sizing is **on by default** (owner decision 2026-10-12) and lazy. The vendor is called only when a trade line has a stated quantity, sizing is on, and the cache entry for the ticker is missing or older than 7 days (`SHARE_COUNT_CACHE_MAX_AGE_DAYS`). `--no-sizing` makes no vendor call and prints the fallback.
- **Cache**: `holdings_share_counts.json` beside the holdings file and the issued-brief log (the `holdings` prefix puts it under N1's `.gitignore` backstop), same directory and file permissions as N1 requires, written atomically; per ticker `count`, the period (`year_report`, `quarter`) and `fetched_at`. Only a value that passed the cross-check is cached. An unreadable or malformed file is treated as empty and reported once. If a fetch fails and a cached value exists, the cached value is used with its fetch date; if neither exists the line falls back. There is no database and no schema change.
- **Withhold rule (replaces the quarter-end rule)**: size is withheld when **(a)** the `ratio_summary()` count differs from any of the four `overview()` `issue_share` values, or **(b)** an issue event that changes the company's count by at least `ISSUE_MATERIAL_RATIO = 1%` has a date after the cached value's `fetched_at` or within `SETTLING_DAYS = 30` days before the run date. The event's date is its ex-rights date, else its record date, else its publication date; a future ex-date counts as after `fetched_at`. The rule is **company-wide**, built on N2a's issue-class enum and its ratio field and does not redefine N2a's investor rule: any class counts (BONUS, STOCK_DIVIDEND, RIGHTS_OFFER, PRIVATE_PLACEMENT, and OTHER with a ratio) when its ratio is at least 1%; EMPLOYEE issues under 1% are ignored (the stored ones are 0.1% to 0.5% each). A non-EMPLOYEE issue whose ratio is missing or 0 (VCB's and VPB's placements are stored with 0.0) has an unknown size and is treated as material; this is a choice made here (open question 12). An announced bonus with no ex-date yet (VCB 2026-04-28) is not a dated change and does not fire until a date appears. `AIS` listing events are not used by this rule.
  - Evidence for (a): on 2026-10-12, 18 days after VPB's ex-date, `ratio_summary()` showed 10,000,000,000 while the four `overview()` values were [10e9, 7,933,923,601, 10e9, 7,933,923,601]. The disagreement is a real signal that the vendor updates its sources at different times.
  - Evidence for (b): when both sources are still equal and old right after an issue, only a window catches it. `SETTLING_DAYS = 30` is a **policy constant resting on one example** (VPB's `ratio_summary()` moved within about 17 days while `overview()` had not converged at 18); the true window is not measured. `ISSUE_MATERIAL_RATIO` is likewise a policy value, not a price-move threshold (Rule 3 is not engaged: it measures a share-count change).
  - The text is "size not shown, because the share count is changing (issue on <date>)" for (b) and "size not shown, because the vendor's two share counts disagree" for (a), each with the read-the-notice checklist: "To size it, read the notice: who filed it, whether it is a sale or a purchase, how many shares in total against the shares outstanding, how it will be done, and the window." (reworded at apply from "who is selling or buying": the owner decision keeps buy, sell and hold out of tool text, and the inflected forms are the same words) This removes the old "withhold until the next quarter row" behaviour and the trigger on trivial employee issues.

Alternative considered: also try other vendor fields or the `market_cap / close` ratio. Rejected: it adds sources to cross-check and the doc found the two named fields agree.

### 9. Size line and benchmark

Size: `quantity / count`, shown with at most two significant figures ("2.3%", "0.016%"), with "of its <count> shares (VCI share count via vnstock, latest-quarter row <year>-Q<q>, fetched <date>)". Not shown when the quantity is missing, sizing is off, the count is unavailable, or the count is changing; each gives the fallback sentence of Decision 8 with its reason first.

Benchmark ("Earlier registrations of this kind in the source ..."):

- Compared set: registrations of the **same direction**, published before this one, with a stated quantity, in the **comparable period**. The period starts at the latest stored issue event that changed the company's count by at least `ISSUE_MATERIAL_RATIO` (or has an unknown size, non-EMPLOYEE) and is **not** one N2a's factor covers (a RIGHTS_OFFER, a PRIVATE_PLACEMENT, an OTHER, or a BONUS or STOCK_DIVIDEND with no ex-date), and is the whole history if none exists. Without this, the cumulative factor would misstate the count at earlier dates. Small EMPLOYEE issues are ignored, so the count at an earlier date can be off by their cumulative size (stored ones are 0.1% to 0.5% each); the sentence calls the share counts estimates.
- Each record's percentage uses the share count at its own date: today's vendor count divided by the factor of N2a's `share_issues_between(events, record date, today)` (SAB: a 100% bonus ex 2023-09-14 halves the pre-2023 count, matching the 641,281,186 in the discussion doc). The record's date is its `published_at`.
- Output: "Earlier registrations of this kind in the source (<k> to <side> with a stated quantity, <first year> onward): <j> were larger than this; the largest of the others was <x>% of the shares then. Each is measured against the share count at its own date, estimated from today's count and the share issues with a ratio in the source." If `j` is 0 the clause reads "none was larger".
- Fewer than 5 comparable records (`BENCHMARK_MIN_RECORDS`) gives "no comparison shown: only <k> earlier registrations with a stated quantity in the comparable period" and nothing else. The benchmark is never shown when the size is not shown.

The sized path did not beat the fallback in the only reading done (1 of 5 sold in each, n = 5, simulated readers), and the benchmark was added for a different observation (3 of 5 did not know if 2.3% is big). Both paths therefore have the same standing in code, tests and wording.

### 10. Footer and fixed text

N1's levels-only footer (in `wording.py`, guarded by its fixed-sentence requirement) is replaced with the v5.3 sentence: "These would make a re-read worthwhile: a registered sale or purchase by a major shareholder or insider, a share issue or capital change, or one of your levels appearing or being reached. Other new announcements are listed for information. Re-run this brief to refresh." The tag text, section headers, fallback and range sentences are constants in one module and are exempt from nothing: the Rule 6 guard scans them.

### 11. Tests and fixtures

No network, no real holdings, no `app.db`, no real titles. Fixtures are synthetic rows shaped like stored ones (fictional tickers and names, the stored title patterns, the stored field names and the measured quirks: publication after the window, missing quantity, duplicate same-day filers, a placement with ratio 0). Injected: the adapter output, the cache path, the fetch function. The vendor fetch is tested with a fake that raises vnai's limiter `SystemExit`, a frame with disagreeing counts, and a frame in the VPB shape. The accuracy check against real titles is a read-only script the owner runs; its result is counts recorded in this file, not a test.

### 12. Small share issues: one quiet summary line (owner decision 2026-10-12)

Issue events below `ISSUE_MATERIAL_RATIO` are not listed individually. Counted as small: an issue with a known ratio above 0 and below 1% of any class, and an employee issue whose ratio is missing or zero. Material and listed: ratio of 1% or more of any class, and a non-employee issue of unknown size (Decision 8).
